# 인천공항 주차 현황

인천국제공항의 주차 가용 면수를 5분마다 수집해 적재하고, 실측 추이와 요일×시간 평균
패턴을 보여준다. 공공 API가 당일 데이터만 주기 때문에 과거 이력은 직접 쌓는다.

페이지는 **건물의 동선 순서**로 읽힌다 — 위에서부터 출국장 혼잡도, 주차 면수, 셔틀
시간표. 차트도 같은 순서다: 예상 여객 → 출국장 대기 → 주차 사용률. 공항에 들어서는
사람이 마주치는 순서와 화면 순서가 같아야 헤매지 않는다.

배치도의 터미널 건물 상자에는 **셔틀 다음 출발 시각**이 붙는다. API에 있는 것이 터미널
순환 셔틀뿐이라(장기주차장 셔틀 노선은 API에 없다) 정류장이 실제로 있는 터미널 건물에만
붙인다 — 장기주차장 상자에 없는 데이터를 붙이지 않는다.

**터미널은 상단 탭으로 고른다.** T1과 T2는 서로 겹치지 않아 동시에 볼 이유가 없고,
한쪽만 보면 선 수가 절반이 되어 화면이 훨씬 읽힌다. 카드·혼잡도·차트·배치도가 모두
고른 터미널 것만 나온다.

카드 아래에는 **출국장 혼잡도**가 게이트별로 나열된다. 합계를 내지 않는다 — 알고 싶은
것은 "몇 번 출국장이 빠른가"이지 합계가 아니고, T2는 같은 출국장을 입구 A~D로 나눠
비슷한 값을 주기 때문에 더하면 부풀려질 위험도 있다. 미운영 게이트는 대기시간 대신
'미운영'으로 표시한다.

요약 아래에는 **편명 검색**이 있다. 편명을 넣으면 오늘 출발편에서 찾아 터미널 탭을
자동으로 맞추고, 출발·변경 시각, 체크인 카운터, 게이트, 공동운항 여부와 함께 **권장
공항 도착 시각(출발 3시간 전 기준 — 규정이 아니라 관례)**과 그 시각의 예상 출국 여객수를
한 카드로 보여준다. upstream 검색은 정확 일치만 지원하고 실제 편명은 `KE703`(0 패딩
없음)·`KE5951Y`(꼬리 문자)처럼 생겨서, 전체 출발편을 10분 캐시로 받아 정규화 매칭한다 —
`KE0703`이라 쳐도 찾아진다. P02(탑승동) 출발편은 체크인·주차가 T1이므로 T1로 안내한다.

주차 카드 아래에는 **요금 계산기**가 있다. 차종(승용/경차/대형)과 감면 대상을 고를 수
있고, 감면율은 전부 공식 페이지(airport.kr 주차요금, 2026-08-25 확인) 기준이다: 경차·
장애인·국가유공자(5·18/고엽제 포함)·다자녀(2자녀 이상, 막내 만 18세 이하)·저공해 1·2종은
50%, 저공해 3종은 20%. **중복 감면은 불가하고 높은 1개만** 적용된다 — 경차이면서 저공해
3종을 골라도 50%다.

공식 페이지 확인 과정에서 계산기 자체의 오류 둘을 바로잡았다. 최초 10분(화물은 45분)
무료가 빠져 있었고, **장기가 "일 단위 올림"으로 구현돼 3시간에 9,000원을 물리고 있었다**
— 실제로는 시간당 1,000원(일 최대 9,000원)이라 3,000원이 맞다. "대형" 요금은 여객
주차장에 없다: 단기는 승용 전용, 장기는 차종 구분 없는 단일 요금이고, 대형에 해당하는
것은 화물터미널 요금(최초 45분 무료·15분당 600원·일 최대 12,000원)뿐이다. 요금 API는 규칙 조각만 주고
어느 주차장의 규칙인지 연결 필드가 없어 계산에 직접 쓸 수 없다 — 공식 요금(단기 최초
30분 1,200원 + 15분당 600원·일 최대 24,000원, 장기 일 9,000원)을 코드에 고정하고, 그
근거 문구가 API 응답에 실재하는지 **매일 수집·대조**한다. 문구가 사라지면 요금이 바뀐
것이므로 계산기에 경고가 붙고 로그에 남는다.

혼잡도 아래에는 **터미널 셔틀 시간표**가 있다 — 정류장별 다음 출발 시각과 첫차·막차·배차
간격. 도착예측 API(getShtbArrivalPredInfo)는 쓰지 않는다: 실측해 보니 예측값이 전부 0이고
일부 행은 2023년에 멈춰 있었다. 시간표(getShtbTimeInfo)는 살아 있어 그걸 쓴다. 시간 값에
`458`처럼 자릿수가 안 채워진 것이 섞여 있어 문자열로 정렬하면 깨진다(실데이터에서 `950`이
막차처럼 보였다) — 숫자로 정규화한다. 평일/휴일 시간표는 서버가 고르는데, 설날·추석 같은
음력 공휴일도 휴일로 잡는다(`holidays` 패키지). 시간표는 이력이 아니므로 DB에 쌓지 않고
12시간 메모리 캐시로 처리하며, 업스트림이 죽으면 낡은 캐시라도 계속 쓴다.

같은 이름의 정류장이 둘 나오는 것(제2여객터미널 ×2)은 API가 실제로 그렇게 주는 것이다 —
승차 위치가 다른 물리적 정류장으로 추정되나 확인하지 못했다.

카드 아래에는 **요약 한 줄**이 있다 — 현재 터미널의 단기주차 사용률과 남은 면수,
출국장 최대 대기(어느 게이트인지 포함), 오늘 출국 피크 시간대. 차 타기 직전에 실제로
알고 싶은 것이 이 세 가지라서다. 전부 이미 받아둔 데이터로 조합하므로 요청이 늘지 않는다.

실측 추이 탭에는 **차트가 셋 상하로** 놓인다. 예상 여객(명), **출국장 대기시간(분)**, 주차 사용률(%) 순이다.
단위가 달라 한 축에 겹치면 어느 쪽도 제대로 안 읽히므로 나누되, y축 폭을 같은 값으로
고정해 **같은 시각이 세로로 정렬**되도록 했다. 한쪽에 마우스를 올리면 **모든 차트에 같은
시각의 십자선**이 그려진다 — 세로로 맞춰둔 이유가 이 비교이므로 각자 놀면 반쪽이다.
두 차트가 같은 x축(수집 시각 배열)을 쓰기 때문에 인덱스가 그대로 대응한다.

여객 색은 **출국이 붉은 계열, 입국이 파란 계열**이다.

실시간 현황은 T1, T2의 3가지 주차 유형(단기/장기/예약) 전체 19개 구역을 대시보드로
확인할 수 있다. 카드에는 남은 자리를 숫자로, 전체 면수와 사용률을 함께 표시하며,
게이지는 "찬 만큼" 채워진다. 요일×시간 패턴은 2~3주 데이터가 쌓인 후부터 확인 가능하다.

실측 추이에는 같은 요일·같은 시각의 평균 사용률이 회색 점선으로 함께 깔린다. 실측선이
그보다 위에 있으면 평소보다 붐빈다는 뜻이다 — 연휴 음영과 겹쳐 보면 "추석 때 평소 대비
얼마나 더 찼나"를 한눈에 알 수 있다. 표본이 3개 미만인 시간대는 기준선을 비워 두므로,
수집 시작 후 2~3주 동안은 점선이 거의 그려지지 않는 것이 정상이다. 범례를 클릭해 끌 수
있다.

차트 아래에는 **주차장 배치도**가 있다. 공항 공식 안내도의 배치를 따른다 — 각 터미널
건물이 맨 위에 있고 아래로 내려갈수록 멀어진다. T1은 남쪽으로 멀어지며 좌측이 서(W),
우측이 동(E)이라 **P2가 서편, P1이 동편**이다. T2는 북쪽으로 멀어지며, 단기주차장만
터미널에 붙어 있고 장기·예약은 도로 건너 북쪽에 있다. 거리는 실제 축척이 아니다.

구역마다 `주차 대수 / 전체 면수`와 사용률을 함께 적는다. 두 숫자의 비율이 곧 옆의
퍼센트라 서로 검산된다 — 상단 카드가 "몇 자리 남았나"에 답하고, 배치도는 "얼마나 찼나"에
답하는 식으로 축을 나눴다.

실측 추이 차트 뒤에는 **시간대별 예상 승객수**가 계단 면적으로 깔린다(오른쪽 축, 명/시간).
출국과 입국을 모두 보여준다 — 출국은 주차 수요를 만들고, 입국은 세워둔 차를 빼가므로
서로 반대로 작용한다. 여객은 시간 단위 데이터라 계단으로 그린다. 5분 축에 부드러운
곡선으로 그리면 실제로 없는 해상도를 있는 것처럼 보이게 한다.

여객 곡선과 평소 기준선은 **구역을 골라도 남는다** — 고른 구역을 그것들과 견주라고
있는 배경 정보이기 때문이다. 범례에는 화면에 실제로 보이는 시리즈만 나온다.

날짜를 내일로 잡으면 여객 예고만 그려지고 주차선은 비어 있다. **예측 지표는 아직
계산하지 않는다** — 요일×시간 칸마다 표본이 몇 개는 있어야 "평소"라고 부를 수 있고,
수집을 2026-08-24에 시작했으므로 3주쯤은 지나야 한다. 그 전에 숫자를 띄우면 표본
하나짜리 평균에 비율을 곱한 값이라 그럴듯하기만 하다.

차트에서 **점선은 오직 평소 기준선 하나**를 뜻한다. 실측선은 전부 실선이다 — 구역이
팔레트 슬롯(8개)보다 많아 색이 돌아오지만, 거기에 점선을 두 번째 구분 채널로 쓰면
화면에 점선이 열 개 넘게 깔려 정작 기준선을 못 알아본다. 어차피 19개를 한꺼번에 읽는
일은 없고, 하나를 고르면 굵은 실선 하나와 점선 기준선만 남는다.

좁은 화면에서는 범례를 감춘다. 19개짜리 범례가 폰 화면의 3분의 1을 먹는데, 구역 선택은
배치도가 하므로 없는 편이 낫다.

사용률은 **소수점 1자리 내림**으로 표기한다. 반올림이면 1,379면 중 1대만 비어도
100%로 보인다 — "100.0%"는 정말 만차일 때만 나와야 한다.

게이지는 혼잡할수록 붉어진다 — 70%부터 주황, 90%부터 빨강이다. 색은 보조 신호일 뿐이고
퍼센트 숫자를 항상 옆에 두므로 색을 구분하지 못해도 정보가 손실되지 않는다.

구역을 누르면 **그 주차장 하나만** 차트에 남는다(나머지는 흐려지는 게 아니라 감춰진다).
19개 선을 한꺼번에 보면 아무것도 읽히지 않고, 무엇보다 마우스를 올릴 때마다 툴팁에 19줄이
쏟아진다. 배치도가 "어디가 찼나"에 답하고 차트는 거기서 고른 하나가 "어떻게 변해왔나"에
답하는 식으로 역할을 나눴다. 같은 구역을 다시 누르면 전체로 돌아온다.

고른 구역이 없을 때는 툴팁이 커서에 가장 가까운 선 하나만 보여주고, 고른 구역이 있으면
그 구역과 평소 기준선 두 줄을 같은 시각 기준으로 나란히 보여준다.

두 가지는 알아둘 만하다. 공개 데이터에 P3 다음이 P5인 것은 **P4가 상주직원 전용**이라
집계에서 빠지기 때문이다(배치도에는 흐리게 표시된다). 그리고 **T1의 P1·P2와 T2의
주차타워 P1·P2는 완전히 다른 부지**다 — 내비게이션에 번호만 넣으면 엉뚱한 터미널로 간다.

수집이 끊긴 구간은 **선을 끊어서** 보여준다. x축을 버킷 간격으로 빠짐없이 채우기
때문인데, 관측된 시각만 축으로 쓰면 6시간 공백이 한 칸으로 압축되고 선은 매끄럽게
이어져 — 측정하지 않은 값을 측정한 것처럼 그리게 된다. 공공 API가 당일치만 주므로
놓친 구간은 영영 복구할 수 없고, 그렇다면 더더욱 비어 있다고 보여줘야 한다.

조회 단위는 **자동 / 5분 / 10분 / 30분 / 1시간** 중에 고른다. 수집은 5분마다 하므로
5분보다 잘게 쪼개는 것은 의미가 없다. 자동은 포인트 수가 감당되는 선에서 가장 촘촘한
단위를 고른다 — 1~3일은 5분, 7일은 10분, 30일은 30분이다. 직접 고른 단위는 자동보다
넉넉한 상한까지 그대로 존중하고(7일치 5분 = 2,016포인트도 그대로 그린다), 그 선을 넘을
때만 굵은 쪽으로 내린다.

두 차트의 세로축은 사용률(%)이다. 주차장마다 규모가 9배까지 차이나기 때문에(T1 예약
1,276면 vs T2 장기 11,093면) 절대 면수로 그리면 큰 주차장이 그래프를 지배해, 작은
주차장이 만차가 되어도 선이 바닥에 눌려 보이지 않는다. 사용률로 정규화하면 규모와
무관하게 서로 비교할 수 있다. 선은 P1·P2 주차장처럼 **개별 구역 단위**로 그린다.

터미널(T1/T2)과 주차 유형(단기/장기/예약)을 각각 다중 선택해 걸러볼 수 있고, 조회 기간은
날짜로 직접 지정한다. 설날·추석처럼 주말과 공휴일이 3일 이상 이어지는 황금연휴는 차트에
음영으로 표시되며, 상단 칩을 누르면 그 구간으로 바로 이동한다. 공휴일은 `holidays`
패키지에서 얻는다 — 설날·추석이 음력 기반이라 계산으로는 구할 수 없기 때문이다.

   ```
   SERVICE_KEY=<인증키>
   ```

   일반 인증키(Encoding 또는 Decoding 모두 가능)를 입력하면 된다.

## 실행

```bash
docker compose up -d --build
```

`http://<미니PC주소>:8000` 접속. 실제 운영에서는 그 앞에 NPM(Nginx Proxy Manager)을
리버스 프록시로 두고 DuckDNS 도메인 + HTTPS로 노출하고 있다 — 앱은 프록시 유무를 모르며
알 필요도 없다(클라이언트 IP를 쓰는 기능이 없다). NPM에는 호스트의 `HOST_PORT`로
프록시하면 된다.

모든 엔드포인트가 읽기 전용(GET)이고 인증이 없다. 외부에 열면 누구나 볼 수 있다는 뜻이다
— 쓰기 경로가 없어 변조 위험은 없지만, 공개 여부는 운영자의 선택이다.

데이터 디렉터리는 로컬 디스크여야 한다. NAS나 네트워크 마운트에 두면 SQLite WAL이 깨진다.

## Portainer로 배포

Portainer는 **Stacks → Add stack → Repository**를 쓴다. 웹 에디터에 compose 내용을
붙여넣는 방식은 이 프로젝트에서 동작하지 않는다 — `build:`에 필요한 소스 컨텍스트가
없기 때문이다.

1. 이 저장소를 원격에 푸시한다 (비공개 저장소로 충분하다).
2. Stacks → Add stack → **Repository**
   - Repository URL: 저장소 주소
   - Compose path: `compose.yml`
   - 비공개면 Authentication에 토큰을 넣는다
3. **Environment variables**에 두 개를 넣는다:

   | 이름 | 값 | 필수 |
   |---|---|---|
   | `SERVICE_KEY` | 공공데이터포털 인증키 | 예 |
   | `DATA_DIR` | `/srv/parking/data` 같은 **절대 경로** | 예 |
   | `HOST_PORT` | 8000이 이미 쓰이면 다른 포트 (기본 8000) | 아니오 |

   `.env` 파일은 만들지 않아도 된다. Portainer가 넣어주는 값이 그대로 치환된다.

   `port is already allocated`로 배포가 실패하면 호스트의 그 포트를 다른 것이 쓰고 있다는
   뜻이다. `HOST_PORT`만 바꾸면 된다 — 컨테이너 안은 계속 8000이므로 앱 설정은 그대로다.
   무엇이 점유 중인지는 `sudo ss -lptn 'sport = :8000'`으로 확인한다.

4. Deploy.

`DATA_DIR`을 반드시 절대 경로로 넣어야 한다. 비워두면 기본값 `./data`가 쓰이는데,
Portainer는 이를 자기 내부 클론 디렉터리(`/data/compose/<id>/data`) 기준으로 해석한다.
스택을 삭제하거나 재클론하면 **몇 달치 수집 이력이 함께 사라진다.**

코드를 고친 뒤에는 push하고 스택 화면에서 **Pull and redeploy**를 누르면 된다.

## API

| 엔드포인트 | 용도 |
|---|---|
| `/api/current` | 구역별 현재 상태 (최근 1시간 내 갱신된 것만) |
| `/api/series?from&to&bucket` | 구간 시계열. 응답 헤더 `X-Bucket-Seconds`에 실제 쓰인 단위가 온다 |
| `/api/pattern` | 요일×시간 평균. 최근 180일, 황금연휴 제외 |
| `/api/passengers?from&to` | 시간대별 예상 승객수 (게이트 단위, 출국·입국) |
| `/api/congestion` | 출국장 게이트별 최신 대기시간·대기인원·혼잡 단계 |
| `/api/congestion/series?from&to&bucket` | 출국장 대기 추이 (버킷 평균) |
| `/api/shuttle` | 터미널 정류장 셔틀 출발 시간표 (평일/휴일 자동 선택) |
| `/api/flight?q=` | 오늘 출발편 편명 검색 (10분 캐시, 정규화 매칭) |
| `/api/fees/estimate?minutes=` | 소형차 예상 요금 (단기/장기) + 요금 변경 감지 |

출국장 대기 추이 차트는 게이트가 아니라 **출국장 번호로 평균** 낸다. 같은 출국장의
동/서(T2는 입구 A~D)는 실질적으로 같은 줄이고, T1 게이트 12개를 작은 차트에 다 그리면
읽히지 않는다. 이 차트의 질문은 "몇 번 출국장이 빨라지고 있나"다.
| `/api/holidays?from&to` | 구간에 걸친 황금연휴 |
| `/api/export.csv?from&to` | 구간의 **원본 행** CSV. 버킷 평균이 아니다 |
| `/api/health` | 모니터링용. 오래됐으면 HTTP 503 |

## 수집 소스

| 소스 | API | 주기 | 호출/일 |
|---|---|---|---|
| `parking` | 주차 정보 (15095047) | 5분 | 288 |
| `passengers` | 승객 예고-출·입국장별 (15095066) | 5분 | 576 (오늘·내일 각 1회) |
| `congestion` | 출국장 혼잡도 T1 (15148225) / T2 (15161098) | 3분 | 각 480 |
| `fees` | 주차장별 요금 부과 기준 (15095053) | 1일 | 1 |
| `spaces` | 주차면 현황 T1 (15107228) / T2 (15160956) | 1시간 | 각 24 / 48 |

**주차면 현황**은 면 단위 입차 시각을 준다. T1 안내문은 "단기주차장만"이라지만 **T2는
장기 평면(lot 12)까지 포함**한다 — 체류 중앙값 31.5시간으로 확인했다. 1.5만 면의 원본을
그대로 쌓는 대신 **구역별 점유 + 체류 히스토그램**(0-3h/3-12h/12-24h/1-3일/3-7일/7일+)만
시간당 1회 저장한다. "3일 이상 주차된 차 수"는 앞으로 출차 예측의 독립 변수가 된다.

두 가지를 거른다. 빈 면(carstatus≠Y)의 입차 시각은 옛 세션의 찌꺼기라 무시하고, 점유
면이라도 입차가 60일을 넘거나 미래면 센서 이상치로 보고 히스토그램에서 뺀다.

**출국장 혼잡도**는 게이트별 대기인원과 대기시간(분)을 준다. 1~2분마다 갱신되고
대기인원은 주차보다 훨씬 빠르게 움직여서 5분은 그 해상도를 버리는 셈이고, 2분(720회/일)은
재시도 여유가 얇아 3분으로 잡았다.

T1과 T2는 **별개 API이고 게이트 체계도 다르다.** T1은 게이트 1~6번을 동/서로 나누고
(`DG1_E`/`DG1_W` …), T2는 출국장 1~2번을 입구 A~D로 나눈다(`DG1_A` …). T2 가이드만 보면
T1도 A~D인 줄 알게 된다. 터미널은 `P01`/`P03`으로 오므로 다른 소스와 맞추려면 `T1`/`T2`로
바꿔야 한다.

두 가지를 조심한다. 대기시간이 60분을 넘으면 **`60+`로만** 오므로 잘렸다는 표시를 따로
남긴다 — 그러지 않으면 62분과 3시간이 화면에서 같아 보인다. 그리고 `operatingTime`이
비어 있으면 **그 시각 미운영**이다. 0명을 '한산하다'로 읽으면 닫힌 곳으로 사람을 보내게 된다.

혼잡도 4단계 기준(가이드): 20분 미만 원활 / 20~40분 보통 / 40~60분 혼잡 / 60분 이상 매우혼잡.

두 데이터셋은 트래픽 한도가 각각 1,000/일이라 서로 깎아먹지 않는다.

**승객 예고**는 시간대별 예상 승객수를 게이트 단위로 준다. 필드명이 `t1eg1~4`처럼
번호로 보이지만 실제로는 구역 이름이다 — 활용가이드 V5.0 기준으로 `t1eg1`은 T1
입국장 **(A,B)**, `t1eg2`는 **(E,F)**, `t1eg3`은 **(C)**, `t1eg4`는 **(D)**다. 번호로
다루면 화면의 "입국장 2번"이 실제 E·F 구역을 가리켜 공항 안내판과 어긋난다.

주의할 점 두 가지. 응답에는 시간대 24행 외에 **`합계` 행이 섞여** 오므로 걸러야
이중 계산을 피한다. 그리고 **`numOfRows`가 `totalCount`보다 작으면 데이터가 조용히
잘린다** — 기본값 10을 쓰면 24시간 중 10시간만 온다(가이드가 명시적으로 경고한다).

주차는 `INSERT OR IGNORE`(같은 관측이 재수집돼도 무시)지만 승객 예고는
`INSERT OR REPLACE`다 — 예고는 갱신되므로 최신 값이 이겨야 한다.

활용가이드 문서(`docs/*.docx`)는 공항공사 배포물이라 저장소에 포함하지 않는다.
공공데이터포털 데이터셋 페이지에서 내려받을 수 있다.

## 수집 소스 추가하기

수집 대상은 `app.SOURCES`에 선언한다. 한 소스가 예외를 던져도 다른 소스는 계속 돈다 —
루프가 소스마다 따로 돌기 때문이다.

```python
class Source(NamedTuple):
    name: str          # 로그와 /api/health에 쓰인다
    interval: int      # 초
    collect: ...       # async (client, con, key) -> 삽입 시도한 행 수
    last_ts: ...       # (con) -> 마지막 수집 epoch 또는 None
```

공공데이터포털은 **데이터셋마다 트래픽 한도가 따로**다. 소스를 늘려도 서로 깎아먹지
않으니, 각 API의 갱신 주기에 맞춰 `interval`을 잡으면 된다.

새 소스의 테이블은 **실제 응답을 한 번 받아본 뒤에** 만든다. 주차 API 때 문서상 9개인 줄
알았던 구역이 실제로는 19개였고 `datetm` 형식도 문서와 달랐다 — 응답을 보기 전에 설계한
스키마는 틀린다.

## 모니터링

`/api/health`는 **소스별로** 마지막 수집 시각과 경과 초를 돌려주고, 그 밖에 행 수,
구역 수, 컨테이너의 `datetime(0,'unixepoch','localtime')` 값을 함께 준다. 하나가 죽고
나머지가 멀쩡할 때 전체를 ok로 묶으면 안 되므로, **소스 중 하나라도 오래되면** 전체가
stale이 된다. 마지막 수집이 1시간을 넘으면
**HTTP 503**을 낸다 — 200을 돌려주면 Uptime Kuma 같은 도구가 정상으로 읽기 때문이다.

이것이 수집기 사망을 알아채는 유일한 자동 신호다. Uptime Kuma나 Portainer 헬스체크에
물려두면 카드가 빌 때까지 기다리지 않아도 된다.

## 운영

시간대가 틀리면 요일×시간 패턴만 어긋나는 게 아니다. `parse_datetm`이 naive local time으로
`ts`를 만들기 때문에, `TZ`가 빠지거나 `tzdata` 패키지가 없으면 저장되는 **모든** 타임스탬프가
9시간 밀린다. 그러면 `db.latest`의 신선도 창(최근 1시간)에 걸리는 행이 하나도 없게 되어
`/api/current`가 빈 배열을 반환하고, **카드도 두 차트도 전부 빈 화면**이 된다. 대시보드가
통째로 비어 있다면 먼저 이 문제를 의심하라.

설정 후 다음을 실행해서 `1970-01-01 09:00:00` (KST)가 나오는지 확인하라.

```bash
docker compose exec parking python -c "import sqlite3; print(sqlite3.connect(':memory:').execute(\"SELECT datetime(0,'unixepoch','localtime')\").fetchone()[0])"
```

`00:00:00`이 나오면 `tzdata` 패키지가 없어서 UTC로 고정된 것이다.

## 법적 사항

위치기반서비스 사업자 신고 대상이 아니다. 주차 잔여 면수는 전기통신설비로 측위된
위치정보가 아니라 시설 점유 현황 통계이며, 개인도 이동성 있는 물건도 식별하지 않는다.

**브라우저 Geolocation API를 사용하지 않는다.** 사용자 위치를 받는 순간 신고 대상이
되며(저장하지 않아도 동일), 미신고 시 3년 이하 징역 또는 3천만원 이하 벌금이다.
